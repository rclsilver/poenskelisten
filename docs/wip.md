## Known bugs / hardening

- **The SSO button shows on additional origins, where OIDC can't complete.** The OIDC flow cookie is set on the origin the user is on, but the IdP callback always goes to `external_url`, so single sign-on started from an `additional_urls` origin fails. Hide the button there, or send the user to `external_url` first. Password login works on every allowed origin.
- **Leaving a group keeps one's wishlists shared with it, out of sight.** `RemoveSelfFromGroup` and `RemoveFromGroup` only disable the group membership, so the group's remaining members can still read (and claim on) the leaver's wishlists. The web UI then hides that share, because `GetGroupMembersFromWishlist` only lists groups the owner is in, so the owner can't see or withdraw it from the web. The MCP's `get_wishlist_sharing` lists such groups (`member: false`, name withheld) and `detach_wishlist_from_group` withdraws them. Fix: either withdraw the leaver's shares when they leave, or list them on the wishlist page so they can be removed.
- **A password reset request answers more slowly for an existing account.** `APIResetPassword` (`controllers/user.go`) sends the e-mail before answering, and only when the account exists, so the response time can still tell which addresses have one, although status and message are the same. It's rate-limited per address now. Fix: send the e-mail in the background and answer at once.
- **Reset and verification codes travel in URL paths** (`GET /api/open/users/reset/:resetCode`, `POST /api/open/users/verify/:code`), so gin's access log on stdout records every code checked. A reset code is valid for a day. Fix: move them into the request body (`web/js/login.js`, `web/js/verify.js`).
- **API messages are English only.** The pages translate their own text, but show the API's error and success messages as they come, and the server-written consent and wrong-origin pages aren't translated.
- **Image uploads are buffered whole, as base64 inside JSON.** A request to the image routes can be 15 MB, held as the body, the decoded JSON string and the decoded bytes (about 40 MB) before the image is looked at. Decoding is limited to two images at a time and those routes to `rate_limit_upload` per account, but a burst of large requests from one account can still take hundreds of megabytes. Fix: upload images separately as binary through a size-limited reader, or bound how many large bodies are read at once.
- **Images stored by older versions over 4 megapixels are served as stored.** Uploads over 4 megapixels are refused, and such a file, kept from before uploads were resized when saved, is no longer decoded to resize it or make its thumbnail, so it is sent full size, thumbnail included. Fix: resize those files once, offline or from the planned orphaned image cleanup on `/admin`.
- **Registered OAuth clients are never cleaned up.** Every connect by an MCP client registers a new one, and the ones no longer used stay in `oauth_clients` (registration is now rate-limited and bounded, and admins can revoke clients).

## Known coverage gaps (intentional, for now)

- **`main()` itself (`main.go:35-130`, ~59 statements) is untested** because it calls `os.Exit` and `log.Fatal(router.Run(...))`. Covering it would mean extracting a `run() error`; not done since coverage is above target without it.
- **Error branches after `utilities.ValidateTextCharacters`/`ValidatePasswordFormat` are unreachable** (~25 sites across `controllers/`): both use constant regexes, so `regexp.Match` never errors. Dropping the `error` return from those validators would remove the dead branches.
- **`utilities/migrate.go`'s per-table foreign-key remapping (inside `ReplaceValues`'s `secondRun` switch, e.g. `groups` → `values[7]` is the owner column) still encodes an unverified legacy schema.** `MigrateSQL`/`ReplaceValues`/`MigrateDBToV2`'s generic mechanics (two-pass scan, CREATE/INSERT detection, bigint→varchar(100) rewriting, numeric-ID→UUID substitution, the synthesized trailing `ALTER TABLE`, and the panic-on-missing-file behavior) have real tests, using a table name that isn't one of the hardcoded special cases — that sidesteps the one part of this file that depends on knowing the exact old-schema column order for `groups`/`wishes`/`invites`/etc., which isn't documented anywhere and would be a guess. The column indices themselves are still unverified (this was inherited legacy code) and a real legacy-schema dump sample or someone who remembers the old schema would be needed to confirm they're actually right — `TestMigrateSQLColumnMappingOutOfRange` in `migrate_test.go` only proves the *mismatch* is now caught. As a defensive measure, `ReplaceValues` now runs each lookup through `mapColumn`, which bounds-checks the index against the row's actual column count and returns a clear error (surfaced by `MigrateSQL`, and by extension panicking `MigrateDBToV2`, same as its other failure modes) instead of either panicking with a raw out-of-range index or silently substituting the wrong column. Low priority since it's not on any live code path for a current install.

## Planned features

- **Resolve the app version without `sed` or a commit on the tag.** Today `config/config.go`'s `poenskelistenVersionParameter` is the literal `{{RELEASE_TAG}}`, and `release.yaml` and `docker-build.yml` (shared by the release and beta image workflows) each `sed` it before building. The old `tag-branch-with-version.yml` also committed the version onto the tag and force-moved the tag, but that made `actions/checkout` in the release workflows fail ("ref does not point to the expected commit") during v2.4.1, so it was removed. As a result, building from the tag's source (a clone of the tag, or GitHub's "Source code" archive) now reports `{{RELEASE_TAG}}`. Plan: one lookup in `config` that takes the first of these that's available, then falls back to `dev`:
  1. **`-ldflags -X`**: a `var version string` set at build time, e.g. `-ldflags "-s -w -X aunefyren/poenskelisten/config.version=<tag>"`. Replace the `sed` `pre_command` in `release.yaml` with go-release-action's `ldflags` input, and in the Dockerfile add an `ARG VERSION` that is passed into its `go build -ldflags`, set through `build-args` in `docker-build.yml` from its `version` input (the release tag, or `beta-<short sha>`).
  2. **`export-subst`**: add `config/version.go export-subst` to `.gitattributes`, with a constant holding `$Format:%(describe:tags=true)$`. `git archive`, which GitHub uses for its source downloads, fills in the tag; in a normal checkout the value stays as the unexpanded `$Format:...$`, which must be treated as "not set". Check that GitHub actually expands `%(describe)` by downloading the archive of a throwaway tag before relying on it.
  3. **`runtime/debug.ReadBuildInfo()`**: since Go 1.24, `go build` in a git checkout stamps `Main.Version` from the tag (`v2.4.1`, a pseudo-version for untagged commits, plus `+dirty` for uncommitted changes). Ignore `(devel)` and an empty value. The Docker build context includes `.git` (it isn't in `.dockerignore`), so this may also kick in there, but (1) takes priority.

  `LoadConfig` persists the resolved version into `config.json` as `poenskelisten_version`, as it does today. Unit-test the precedence with the ldflags/`export-subst` values as package variables that tests can override.

- **Orphaned image cleanup on `/admin`.** Deleting a wish, wishlist or user now removes its image files, but files left behind by deletions made before that change are still on disk. Plan: a section on the admin page (`web/html/admin.html` / `web/js/admin.js`) with two admin-only endpoints under `/api/admin`:
  - A read-only scan listing orphaned files and their total size. That means any `images/wishes/<id>{,_thumbnail}.jpg` whose wish doesn't exist, is disabled, or is on a disabled wishlist, and any `images/profiles/<id>{,_thumbnail}.jpg` whose user doesn't exist or is disabled. Stray `.upload-*.jpg` temp files from interrupted writes count too.
  - A delete action the admin confirms explicitly, which removes exactly what the scan found.

  Keep the scan and the delete as separate steps, since the delete removes user files for good. The filesystem walk belongs in `controllers/image.go`, and the "which of these IDs are still live" lookups in `database/`, which keeps the layering rule.
